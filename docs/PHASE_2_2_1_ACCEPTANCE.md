# Phase 2.2.1 — Critical completion and acceptance hardening

This document records the additional implementation on PR #5. It is not a claim of production certification.

## Implemented

### Central scanner eligibility

- Added app.domain.scanner_eligibility.validate_scanner_eligibility as the shared final eligibility decision.
- Every MarketScanner candidate is passed through the gate immediately before it is persisted and appended to the eligible opportunity list.
- The gate evaluates required Spot/Futures fields, finite positive prices and volumes, field age, WebSocket health when WebSockets are enabled, clock synchronization/drift, exchange filter completeness, funding freshness, current-versus-latest-realized funding reconciliation and unresolved funding gaps, theoretical hedge validation, residual exposure and visible order-book depth.
- Each decision includes eligible, status, checked_at_ms, stable rejection codes and human-readable explanations.
- Early scanner pre-filter rejections are also exposed with structured codes.
- The legacy build_opportunity helper refuses eligibility when complete gate evidence is not supplied; it cannot independently label a candidate eligible.
- GET /api/v1/scanner/eligibility returns the same decision objects generated by the scanner.

### Observation lifecycle

- Added persistent symbol-level state and per-scan opportunity snapshots to ValidationStore.
- Stable identity is the strategy/symbol pair; this repository currently has one fixed Spot-long/USDⓈ-M-short strategy.
- Persists appearance/disappearance, eligibility, rejection-code, ranking, funding, basis, liquidity, data-quality and WebSocket-health changes, including diagnostic changes for rejected symbols.
- No change event is emitted when the compared state is unchanged.
- State is read from SQLite after restart, so the next scan compares against persisted state rather than an empty in-memory baseline.
- Scanner run start/end, candidate counts and expected interval are persisted when observation mode is enabled.

### Statistical reports

- Added daily UTC and cumulative report endpoints.
- Reports are calculated from persisted scanner runs, opportunity snapshots and lifecycle/connection events.
- Includes measured observation duration, run counts, appearance/disappearance and eligibility/ranking transitions, completed opportunity durations, funding/basis/liquidity/freshness distributions, rejection-code counts, scanner interval gaps, recovery durations and WebSocket uptime where connection-transition evidence exists.
- Uptime is not inferred before the first persisted connection event. Daily uptime is clipped to the requested UTC report period.
- null means there is not enough persisted evidence for a statistic.

### Funding reconciliation

- Added a paginated helper that returns deduplicated settlements and a duplicate count.
- Validation checks timestamps and rates, detects interval gaps, backfills bounded missing windows, compares the current observed lastFundingRate with the latest historical realized rate, and reports unresolved gaps explicitly.
- Missing settlements are never synthesized as zero. Future funding remains unknown until realized.
- Reconciled records are stored in the existing funding history table when the market store is supplied.

### WebSocket reliability

- Connection/disconnection/recovery events are persisted.
- Initial connection is distinct from recovery.
- Reconnect attempts and successes are counted per shard rather than treating every shard's initial connection as a reconnect.
- Market-level connection transition events are emitted only when the aggregate market feed changes between all-down and at-least-one-shard-connected.

## New tests

- Shared gate healthy case and deterministic rejection cases for stale/missing/invalid fields, unhealthy WebSocket, clock drift, invalid filters, stale/inconsistent funding, invalid funding timestamp, invalid hedge, excessive residual exposure and insufficient depth.
- Lifecycle duplicate suppression, funding/basis changes, disappearance and SQLite reopen.
- Daily period filtering, persisted scan duration and scanner interval gap detection.
- WebSocket connection failure, reconnect success and repeated reconnect failure using mocks.
- Funding duplicate detection, backfill success and unresolved gap reporting.
- Existing hub tests cover duplicate/out-of-order/delayed/future timestamp rejection and stale/missing field handling.

## Read-only boundary

No API credentials, authenticated account endpoints, balances, positions, order placement/cancellation, leverage/margin changes, transfers or withdrawals are implemented. No live-trading switch has been added. Observation, live validation and WebSockets remain opt-in.

## Remaining limitations

- Public Binance integration tests remain opt-in. Unless explicitly enabled and executed, CI is not evidence of real Binance connectivity.
- A one-message WebSocket probe and deterministic mocked recovery tests do not certify long-duration connection stability.
- Funding interval detection remains heuristic; reconciliation is bounded to ten pages for the initial fetch and ten detected gaps with up to five pages each. Any unresolved interval remains a warning and blocks scanner eligibility.
- Report distributions describe persisted eligible opportunity snapshots, not every symbol in the exchange universe. Rejection distributions describe persisted scanner rejection decisions.
- Uptime is measurable only from persisted connection transition events during the running observation period; downtime before the first event or before process startup is unknown.
- Theoretical hedge checks do not include account balances, margin, liquidation, account fee tiers, or actual fills.
- SQLite is intended for a single application process. Use a VPN or authenticated reverse proxy before remote API access.
- No real-money or paper-trading performance is established by this phase.
